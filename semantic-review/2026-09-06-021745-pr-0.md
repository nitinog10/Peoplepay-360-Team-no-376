# Payroll-manager controls and live payroll dashboard

Phase 4 releases payroll-manager configuration and hard-delete permissions, adds editable salary structures/rules, and introduces a live dashboard spanning payroll, attendance, leave, and alerts. The direct route gates and frontend mutation controls use the new permissions, DRAFT payrun deletion is status-constrained, and payslip-line snapshots preserve rule amounts across later rule edits. Blocking findings remain because lower roles can grant themselves the new manager role through user administration, and dashboard money is summed across currencies while being labeled as the default currency. The new individual-payslip delete also has a lifecycle race that can remove a slip after its payrun has crossed out of DRAFT.

Watch for: **blocking, confirmed** lower-role elevation into `HR_PAYROLL_MANAGER`; **blocking, confirmed** mixed-currency totals labeled as `DEFAULT_CURRENCY`; **high, likely** deletion crossing the DRAFT/COMPUTED boundary; **high, confirmed** mutable structure names changing historical paid-payslip output.

**Verdict**: NEEDS_CHANGES

## High-level view

The new permission names are consistently applied at the salary-config, payrun-delete, and payslip-delete routes, and the corresponding buttons use `useCan`. That boundary is nevertheless bypassable with **confirmed** confidence: `HR_MANAGER` and `HR_PAYROLL_USER` retain `users:manage`, while `HR_PAYROLL_MANAGER` is now an unrestricted assignable role, so either lower role can change another account’s role and password and then use the manager-only operations.

The lifecycle design distinguishes DRAFT hard deletion from later-state cancellation, and stored payslip lines correctly snapshot rule inputs and amounts. Two integrity gaps remain: with **likely** confidence, an individual payslip delete can act on a stale DRAFT check after a concurrent compute commits; with **confirmed** confidence, a referenced salary structure can be renamed while historical paid-payslip detail and PDF generation continue to resolve the current name.

The dashboard builds one response from a shared employee cohort and period, but several metrics do not share the same semantics. With **confirmed** confidence, money from arbitrary contract/payrun currencies is added and labeled with the environment default; the contract-type cohort is applied differently to payroll versus attendance/leave; overlapping leave contributes days outside the selected period; and the overall attendance-health formula can count one unhealthy day twice.

The configuration editor permits useful atomic sequence swaps and preserves historical line snapshots, but with **confirmed** confidence it does not validate the resulting formula dependency graph. Formula syntax/references, rule-code renames, and reorders can therefore be accepted even though the next payroll computation will fail.

The dashboard and config pages are permission-gated in the UI, but filtered KPI links have a **confirmed** consistency gap: only `from` and `to` survive navigation, so department and employee-type selections disappear and the destination lists cannot reproduce the displayed cohort. The passing static and unit gates do not cover these boundaries; the Phase 4 smoke assertion checks dashboard shape and seeded happy-path totals rather than mixed currencies, boundary overlaps, role elevation, or concurrent transitions.

## Manager-only permissions are self-service through user administration

The new catalogue makes `HR_PAYROLL_MANAGER` assignable in `ts-backend/src/auth/permissions.ts:93`, while `HR_MANAGER` and its payroll supersets retain `users:manage`. The users router authorizes solely on that permission (`ts-backend/src/modules/users/router.ts:9`), and both create and update resolve any value in `ASSIGNABLE_ROLE_NAMES` without comparing the actor’s role to the target role (`ts-backend/src/modules/users/service.ts:21-24, 72-83, 87-102`). The self-role guard does not close the path: a lower-role operator can update another account to `HR_PAYROLL_MANAGER`, set a known password in the same request, and log in as that account. The frontend exposes the same option in `frontend/app/(app)/users/user-form-dialog.tsx:19-50`.

This is a **blocking, confirmed** authorization bypass because it makes `salary-config:write`, `payruns:delete`, and `payslips:delete` manager-only only for direct requests, not for an actor willing to use the existing account-management screen first. The plan explicitly defers narrowing `users:manage` until Phase 5, but Phase 4 now places destructive payroll privileges behind the bypassed role. Enforce an actor-aware role ceiling now—at minimum, refuse `HR_PAYROLL_MANAGER` assignment by lower roles and pass the actor into create as well as update—or keep the role non-assignable until an administrator can grant it.

## Dashboard money collapses distinct currencies into `DEFAULT_CURRENCY`

Contracts accept caller-selected three-character currencies, salary structures now do the same, and payrun creation only requires each selected contract to match its chosen structure. The dashboard then adds every selected payslip’s raw `net` into `salaryCost`, `totalNetPaid`, department totals, and monthly totals (`ts-backend/src/modules/dashboard/service.ts:165-179`) without grouping or converting currencies, and returns `env.DEFAULT_CURRENCY` as the label for all of them (`ts-backend/src/modules/dashboard/service.ts:301`). A USD 1,000 payslip and an INR 1,000 payslip are consequently reported as INR 2,000 when INR is the default.

This is a **blocking, confirmed** financial-reporting defect, especially because the payroll design explicitly has no implicit currency conversion. Make currency part of the filter and reject heterogeneous result sets, return all monetary aggregates grouped by currency, or perform an explicit auditable conversion; the response must not infer a singular display currency from configuration unrelated to the selected rows.

## DRAFT payslip deletion can cross the compute boundary

Payrun deletion uses a status predicate in the delete itself, but individual payslip deletion first reads the parent status and then issues an unconditional delete by payslip id (`ts-backend/src/modules/payslips/service.ts:144-154`). Compute holds a transaction while recalculating slips and changes the payrun to `COMPUTED` only at the end. A delete that reads DRAFT while compute is in progress can wait on the payslip lock, resume after compute commits, and delete the newly computed slip; warnings and validation then iterate only the remaining slips, so the run can continue without the removed employee.

This is a **high, likely** lifecycle race based on the separated check/mutation and the compute transaction’s ordering. Make the delete conditional on the parent still being DRAFT at mutation time, using a transaction/lock or a relational `deleteMany` predicate followed by explicit not-found versus wrong-state handling. Add a concurrency integration test that pauses compute between its initial status read and commit.

## Paid payslips still resolve mutable structure identity

Salary-structure PATCH permits name changes even when payruns reference the structure (`ts-backend/src/modules/salary-structures/service.ts:73-83`). Payslip detail and PDF loading do not use a payrun snapshot for that identity; they join the current structure name (`ts-backend/src/modules/payslips/service.ts:23-26`, `ts-backend/src/modules/payroll/pdf.ts:10-13, 56-57`). Renaming a structure after a payrun is PAID therefore changes both the historical API representation and a regenerated payroll document, even though its rule lines and monetary totals remain stable.

This is a **high, confirmed** historic-immutability gap. Snapshot the structure display name on the payrun/payslip and render historical artifacts from that snapshot, or version structures and bind each payrun to an immutable version. The existing rule-line snapshots are the right pattern and should be extended to the structure metadata that appears on the document.

## Contract type and period mean different things across dashboard widgets

The dashboard first admits an employee when any contract of the selected type overlaps the requested range (`ts-backend/src/modules/dashboard/service.ts:73-83`). Payroll rows then apply the type again to the exact contract linked to each payslip (`ts-backend/src/modules/dashboard/service.ts:106-112`), while attendance and time-off rows use only the admitted employee ids (`ts-backend/src/modules/dashboard/service.ts:119-130`). If an employee changes from PERMANENT to CONTRACTOR during the range, a PERMANENT dashboard excludes contractor payslips but includes attendance and leave from the contractor portion.

This is a **high, confirmed** uniform-filter defect. Define employee type either as one cohort property for the entire response or as an effective-dated property for every row, then apply that definition to payroll, attendance, leave, alerts, and department counts consistently.

The period filter has a separate **medium, confirmed** boundary error for leave. Requests are selected by overlap, but the service sums their full stored `totalDays` (`ts-backend/src/modules/dashboard/service.ts:123-130, 213-224`); a five-day request with one day inside the dashboard range contributes all five days. Recompute days for the intersection with `from`/`to` using the effective schedule, or label and contract the metric as full duration of overlapping requests rather than days in period.

## Attendance health double-penalizes one record

Department health increments `healthy` only when a present record is neither late nor missing checkout, but the top-level KPI derives healthy days as `present - late - missingCheckouts` (`ts-backend/src/modules/dashboard/service.ts:183-207, 280`). A record that is both late and missing a checkout is subtracted twice. With one healthy day and one day carrying both faults, the KPI reports 0% while the matching department row reports 50%.

This is a **medium, confirmed** correctness defect. Count top-level healthy records with the same per-record predicate used for departments, rather than deriving a union count from two overlapping fault totals.

## Rule mutations can save an unusable formula graph

Create and update validate only the operand required by the selected method plus uniqueness (`ts-backend/src/modules/salary-rules/service.ts:31-44, 90-107, 110-145`). Reorder validates ownership and sequence uniqueness, then writes the requested sequence values (`ts-backend/src/modules/salary-structures/service.ts:87-113`). None of these operations validates formula syntax/references against the resulting active rule set. A manager can move a referenced rule after its consumer, rename a code still named in `rules['CODE']`, or save an unknown reference; the mutation returns success, while `executePayroll` later rejects it as an unknown/current/later rule.

This is a **high, confirmed** configuration-correctness gap because a successful editor action can make all subsequent computations for the structure fail. Validate the complete resulting active rule graph within the create/update/reorder transaction, including allowed syntax, referenced codes, and sequence direction; preserve runtime checks for data-dependent failures such as division by zero.

## Filtered dashboard cards navigate to a broader population

The dashboard API query includes period, department, and contract type, but the shared KPI query string contains only `from` and `to` (`frontend/components/payroll/payroll-dashboard.tsx:42-52`). Every KPI link at lines 60-64 therefore drops department and employee type. The payslip destination API/list has no department or contract-type filter, so adding the omitted parameters only at the link would not yet make the drill-down match.

This is a **medium, confirmed** frontend filter-consistency gap. Extend destination list contracts to express the dashboard cohort and preserve all active filters in links, or stop presenting the cards as drill-downs until an equivalent result set can be shown.

## Verification does not exercise the new failure boundaries

The local gates pass: backend typecheck, 82/82 unit tests, frontend typecheck, and ESLint are green. The smoke suite confirms direct permission denials, CRUD/lifecycle happy paths, paid rule-line snapshots, and dashboard response shape, but its role assertion only checks that the manager is assignable (`ts-backend/scripts/smoke.ts:281-285`) and its dashboard assertion only checks nonempty sections (`ts-backend/scripts/smoke.ts:492-500`). There are no dashboard service tests or config/lifecycle service tests for mixed currency, cross-contract periods, clipped leave, overlapping attendance faults, formula-graph mutations, or concurrent deletion.

This is a **medium, confirmed** regression-coverage gap. Add focused service/integration cases for each boundary above; direct-query reproduction over one seeded currency verifies arithmetic against the implementation but cannot establish the intended semantics at filter and lifecycle edges.
